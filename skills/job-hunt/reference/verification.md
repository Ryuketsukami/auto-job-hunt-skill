# Verification: what counts as proof

One principle underneath all of it:

> **Nothing is taken on trust from the step that produced it.**

A CV that was rendered is not a CV that fits on one page. A form that was filled is not an
application that arrived. A row that was written is not a row that parses. The step that did the
work is the worst possible witness to whether it succeeded.

Second principle, and it is the one that gets broken:

> **Your own log is not evidence about the world.**

A script that printed `SUBMITTED` proves the script reached that line. It does not prove an employer
received anything. Proof of a send comes from the employer's side: a confirmation page, a message-id
from the mail server, an acknowledgement email. Never from your own output.

---

## Commands

The claims and their proofs are in the "Verify before you claim" table in SKILL.md. This is how to
run each one. `<dir>` is `<ws>/people/<p>/roles/<batch>-<company>-<role>`.

| SKILL.md claim | Command |
|---|---|
| CV fits one page | `python3 <skill-dir>/scripts/render.py <dir>` |
| Voice and fingerprint rules hold | `python3 <skill-dir>/scripts/preflight.py <dir>` |
| Handling instructions respected | the same preflight run; it reads the person's `.preflight` |
| CV is on-target | `score N` in the ledger notes, repeated in the report |
| Ledger updated | `python3 <skill-dir>/scripts/ledger.py --person <p> find --url <url>` |
| Application arrived | screenshot in `<dir>`, the mailbox, or the SMTP response |

Checks SKILL.md does not list:

| Claim | Proof | Command |
|---|---|---|
| PDF text is extractable | the real words come back | `pdftotext <pdf> - \| head -40`, when poppler is installed |
| Both CSVs intact | exit 0, no output | `python3 <skill-dir>/scripts/ledger.py --person <p> validate` |
| Employer replied | the message in the mailbox | Gmail connector search, or `mailbox.py --person <p> search 'FROM "..."'` |

## Verifying the render

`render.py` prints the CV with a Chromium-based browser (Chrome, Edge, or Chromium; set
`JOB_HUNT_BROWSER` to a browser path if none is found), reads the page count straight out of the PDF
bytes, prints `pages N`, and exits 1 unless a CV is exactly one page. On success it copies the PDF
into `cvs/<dir-name>.pdf`.

The count is read from the bytes because `pdfinfo`, `qpdf`, `mutool`, and `gs` are commonly
absent. `pdftotext` and `pdftoppm` (poppler-utils) are more often present and are worth using when
they are: `pdftoppm -png -r 60 <pdf> page` gives an image to check for a mostly empty page, which a
page count cannot see.

**A multi-page artifact is never delivered without saying so.** Say the page count out loud.

## Verifying voice and fingerprints

`preflight.py <dir>` checks every `.html` file in the role directory and fails on any of:

- **Third person**: he, she, his, hers, or the person's own name as the subject of their bullet.
- **First person** in a CV: I, my, me. The CV voice is the implied subject. (Cover letters and
  emails are first person, and preflight knows the difference by file name.)
- **Agent fingerprints**: "generated by", "as an AI", "based on the provided", meta-commentary,
  leftover `{{TEMPLATE}}` markers, placeholders, TODO.
- **Assistant-register phrasing** and **em dashes or spaced en dashes**.
- **Disclosure of an omission or a stretch**: `(omitted)`, `(approx.)`, `(see note)`.
- **Any term in the person's `.preflight` file.** One term per line, `#` comments allowed.
- **Contact details that are not links**: a visible email or LinkedIn URL without an anchor.

Exit 0 or the CV does not render. It is not optional and not advisory.

## Verifying a send

Acceptable proofs, strongest first:

1. **An acknowledgement email from the employer** in the person's mailbox. It proves the
   application reached a system that decided to answer.
2. **A message-id returned by the mail server** for an email application. Proves it left; not that
   a human will see it.
3. **A confirmation page**, named specifically: a URL ending `/confirmation` titled "Thank you for
   applying", a form that replaced itself with "Thank you!", a board's own applied banner.
   Screenshot it into the role directory.

**A missing acknowledgement is not a failure when the confirmation page was seen.** Many employers
and boards send none.

Not acceptable: a script that logged success, a body-text match on `thank you|submitted|received`,
a `200` status code, or the absence of an error.

---

## Verifying a sub-agent

When drafting is parallelised across roles, verify the returned work against the brief, not against
the sub-agent's summary. Read one bullet from the CV it says it wrote. Run preflight and render
yourself. An agent's report describes what it intended to do.

---

## When verification fails

- **File write**: revert to the prior content, retry once, then stop and say so.
- **Render**: fix and re-render. Two reflow passes maximum; a third means the content is wrong, not
  the layout.
- **Form submission**: two attempts, then park it. Never a third variation.
- **Ledger validate**: stop writing rows and fix the cause. Never hand-edit a CSV to make it pass.
- **A fact that will not resolve**: it goes to `## Open questions` in `profile.md` and is unusable
  until the person answers.

Failing loudly is the point. A pipeline that silently downgrades a blocked application into a sent
one is worse than a pipeline that stops.
